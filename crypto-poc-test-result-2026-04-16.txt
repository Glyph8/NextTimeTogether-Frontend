4) 테스트 범위 상세 설명 (핵심)
결론: 이 벤치마크는 "단순 데이터 전달 테스트"가 아니라, 실제 Web Crypto API 연산을 포함한 테스트임.

4-1. 실제 crypto.subtle 암호화/복호화 포함 여부
- 포함됨.
- 입력 준비 단계에서 encryptDataClient(...)를 사용해 payload를 실제 AES-GCM 암호화함.
- encryptDataClient 내부에서 crypto.subtle.encrypt(...)를 호출함.
- Main 경로는 crypto.subtle.decrypt(...)로 암호문 전량 복호화.
- Worker 경로도 worker 내부에서 키 import 후 crypto.subtle.decrypt(...)로 동일 암호문 전량 복호화.

4-2. 무엇을 비교하는 테스트인가
- 같은 암호문 리스트와 같은 키를 기준으로
  - Main thread 복호화 시간
  - Worker thread 복호화 시간
  을 비교.
- LongTask 관찰값도 함께 수집.

4-3. Worker 경로에서 추가로 개입되는 비용
- postMessage 전달/직렬화
- 스레드 전환 및 워커 생성/종료 관련 오버헤드
- 따라서 현재 페이로드 크기에서는 Worker의 부가비용이 복호화 병렬/오프로딩 이득을 상쇄하거나 초과할 수 있음.

4-4. 측정 제외 항목
- 네트워크 I/O 없음
- 서버 API 호출 없음
- DOM 렌더링 비용 직접 측정 아님
- 암호문 생성 단계는 Main vs Worker 복호화 비교 구간 이전에 선행됨

5) 종합 해석
- 제공된 전체 측정에서 Winner는 일관되게 Main.
- LongTask가 지속적으로 0이므로, 현재 조건에서는 Worker 오프로딩의 UI 응답성 개선 근거도 확인되지 않음.
- 현 페이로드/환경에서는 "메인 스레드 유지"가 더 합리적인 선택으로 해석 가능.
